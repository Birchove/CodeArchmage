# ADR-002：SQLite 访问策略——同步 sqlite3 + asyncio.to_thread

- **状态**：提议（待 cc 审核后定稿）
- **日期**：2026-08-13
- **决策者**：CodeBuddy（主分析），cc（第二意见待审）

## 背景

FastAPI 是异步框架，SQLite 访问有两种技术方案：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. aiosqlite** | 原生异步库 | API 自然，无心智负担 | 多一层包装、性能略低、额外依赖 |
| **B. sqlite3 + asyncio.to_thread** | 标准库同步访问，用 `to_thread` 桥接到异步 | 性能最优、零依赖 | 需自行管理线程安全 |

## 决策

**采用方案 B：同步 `sqlite3` + `asyncio.to_thread`，启用 WAL 模式。**

## 理由

1. **负载特征匹配**：Code Archmage 是单用户、单仓库的本地工具，读多写少。WAL 模式下读不阻塞写，线程池完全够用，不存在高并发压力。

2. **aiosqlite 本质也是线程池**：`aiosqlite` 内部就是把 `sqlite3` 调用丢到线程池里执行，多一层抽象对单用户场景无收益，反而增加依赖和调试复杂度。

3. **标准库零依赖**：`sqlite3` 是 Python 标准库，不需要额外安装。符合"小而美"、减少安装体积的原则。

4. **Python 3.11+ 的 `asyncio.to_thread`** 让同步→异步桥接非常简洁（项目已定 Python 3.11+ 基线）。

5. **阶段 2（索引器）是纯同步逻辑**：索引器本身不涉及异步，用同步 `sqlite3` 写入和查询最自然。异步包装留到阶段 3（服务层）再加，分层清晰。

## 实现约定

1. **分层**：阶段 2 索引器用纯同步 `sqlite3`（无 async）；阶段 3 服务层用 `asyncio.to_thread` 包装索引器的同步查询函数。
2. **连接管理：一个工作单元一个连接**（per-request / per-file connection，打开即用、用完即关）。**不使用单连接 + `check_same_thread=False`**——`asyncio.to_thread` 用多线程执行器，多个并发请求会并行执行查询，共享连接会踩 `sqlite3` 的隐式事务坑（一个连接同一时刻只能有一个活跃事务，线程 A 的 `fetchone` 可能把线程 B 的语句结果吃掉，或触发 "recursive use of cursors not allowed"）。WAL 解决的是"读写互不阻塞"，解决不了共享连接的游标交错。SQLite 连接开销是微秒级，WAL 下多连接读写天然并发安全。
3. **WAL 模式**：建库时执行 `PRAGMA journal_mode=WAL`，支持"索引中也能查询"。
4. **查询封装**：纯函数风格，输入 `(conn, 查询参数)` → 输出 dataclass 结果，便于单元测试（用 `:memory:` 跑）。每个调用方自己开 conn 传入。
5. **事务**：索引单个文件用单个事务，**事务内先按 `file_path` 删除旧数据（symbols/calls/imports），再插入新数据**（原子性的先删后写，保证增量索引不产生孤儿数据）。

## 后果

**正面**：
- 性能最优，无额外抽象层
- 标准库依赖，减少安装体积和依赖冲突风险
- WAL 模式支持并发读写（索引中可查询）
- 索引器层保持纯同步，测试简单（无需 async 测试框架）

**负面**：
- 服务层需用 `asyncio.to_thread` 桥接，多一层心智模型（可接受）
- 需注意 `sqlite3` 连接的线程安全（`check_same_thread=False` + 单连接时需确保查询是原子的）

## 何时重新评估

- 如果未来转向多仓库并发索引（不太可能，但万一），需重新评估连接池策略
- 如果 SQLite 性能成为瓶颈（大仓库 >10 万符号），考虑改用 `apsw`（另一个 SQLite 绑定，性能更好）
