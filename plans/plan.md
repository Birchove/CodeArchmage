# Code Archmage — 源码拆解工具 · 产品技术规划（v2）

> 项目代号：Code Archmage（代码大法师）
> 目标：帮助初出茅庐、缺乏工程锻炼的大学生，拆解并理解动辄几万行的工程化源码。
> 原则：小而精美，只做"拆解源码"这一件事。
> 本版整合了 3 份 AI 文档（深度研究报告 / 产品蓝图 / PRD）+ Claude Code 第二意见 + CodeBuddy 判断。

## 一、形态决策：本地优先（Local-First）的只读代码拆解器

### 候选方案对比

| 方案 | 优点 | 致命缺点 | 结论 |
|------|------|----------|------|
| **A. VSCode/Cursor 插件** | 用户已在编辑器内，零迁移成本 | 编辑器满屏按钮是噪音放大器；插件 UI 做不出小而美；Cursor 自带 LLM 重复造轮子 | ❌ 排除 |
| **B. 云端 Web 应用**（PRD 倾向） | 零安装、验证快 | ① 输入是学生本地代码（实习/私有仓库**不能**上传，不是"未必愿意"）；② 服务器+LLM 代理+隐私合规成本对小团队是负担；③ 浏览器标签旁就是 B 站，破坏"阅览室"调性 | ❌ 排除 |
| **C. 纯桌面应用**（蓝图倾向 C++/Qt） | 沉浸、离线、性能 | 第一天就上 Tauri/Qt 增加打包分发成本；Qt 放弃整个 Web 生态 | ⚠️ 节奏不对 |
| **D. 本地优先 + Web 技术栈**（最终选择） | 见下 | 用户首次要跑一条安装命令（对大学生可接受） | ✅ **采纳** |

### 最终决策：方案 D —— 本地优先（Local-First），三层解耦

```
引擎层（Python: tree-sitter 解析/索引/查询）
    ↓ localhost REST/WebSocket
本地服务层（FastAPI，一条命令启动）
    ↓ http://localhost:port
Web UI（React + TS，浏览器打开 localhost）
```

**演进路径**：MVP 以"一条命令启动、浏览器打开 localhost"发布 → 验证通过后套 Tauri 壳变成真正的桌面应用，**代码 100% 复用，两种形态只差一个壳**。

**核心理由**（cc 的关键洞察，我完全采纳）：

1. **数据流决定形态。** Code Archmage 的输入是"学生本地已有的代码"——课程作业、实习仓库、clone 下来的开源项目。Web 化意味着"上传/git clone 到服务器 → 服务器索引 → 回传展示"，这是把天然本地的工作流搬到云端，换来的唯一好处是"省一次安装"。对大学生来说装一个桌面软件的成本接近于零（他们天天装 VSCode、Steam、Discord）。

2. **隐私理由比最初说的更强。** 实习代码、公司内部代码是真的**不能**上传，不是"未必愿意"。DeepWiki 的 Web 模式成立是因为它只索引公开仓库 + 有 Devin 导流兜底服务器成本——这两个条件我们都不具备。

3. **"阅览室调性"是决定性的。** 一个独立的、全屏的、安静的应用窗口，本身就是产品价值。浏览器标签页旁边就是 B 站和微信。

4. **Tauri vs C++/Qt：选 Tauri，不用犹豫。** 对只读阅读器来说性能不是瓶颈——瓶颈在索引速度（tree-sitter 的 CPU 活，和壳无关）和大文件渲染（虚拟滚动就能解决）。Qt 在这个负载上的性能优势约等于零，代价却是放弃整个 Web 生态（CodeMirror、react-flow、d3）和翻倍的 UI 开发成本。

## 二、GUI 必备功能（四区布局）

```
┌─────────────┬──────────────────────────┬──────────────┐
│ ① 文件树     │    ③ 代码视图（只读）       │  ⑤ LLM 对话  │
│ ② 符号大纲   │    ④ 关系/调用图面板        │   面板        │
└─────────────┴──────────────────────────┴──────────────┘
              ⑥ 全局搜索栏（顶部）
```

| 区 | 功能 | 说明 |
|----|------|------|
| ① 文件树 | 目录层次 | 结构骨架 |
| ② 符号大纲 | 当前文件的函数/类/变量，可折叠跳转 | 类 Source Insight Symbol Window |
| ③ 只读代码视图 | 高亮 + 行号，点击符号→跳定义/查引用/查调用者 | CodeMirror 6 只读模式 |
| ④ 调用图面板 | 调用树、类继承树、引用树 | react-flow，默认只画当前节点上下游 1-2 层 |
| ⑤ LLM 对话 | 选中代码即问，**自动注入符号上下文** | "代码家教"不是"生成器" |
| ⑥ 全局搜索 | 对整个项目做符号/文本搜索 | SQLite FTS5 全文索引 |

### 针对 4 大痛点的差异化功能

| 痛点 | 功能 |
|------|------|
| ① 封装套封装，不知其用 | **「剥洋葱」**：深层调用链一键展平成线性栈；**「模块卡片」**：惰性生成的目录职责说明 |
| ② 没见过的写法 | **LLM「这是什么写法」**：选中陌生语法一键解释 |
| ③ 复杂接口/边界 | **调用图 + 引用追踪**：谁调用了它、参数从哪来、边界在哪检查 |
| ④ 关键算法 | **LLM「讲讲这个算法」**：逐步讲解 + 数据流 |
| （隐藏）无从下手 | **「阅读路径」**：自动识别入口/核心文件，推荐阅读顺序 |

## 三、做什么 / 不做什么（边界）

### ✅ 做（MVP 范围）
- 只读浏览 + 语法高亮（**MVP 仅 Python**，TS 为验证后第一候选）
- 符号索引：定义跳转、引用查找、调用者/被调用者、调用图、类继承图
- 文件树 + 符号大纲 + 全局搜索（FTS5）
- 内置 LLM 对话（解释为主）+ **确定性上下文自动组装**（必做，非可选）
- 「剥洋葱」调用链展平

### ❌ 不做（明确排除）
- ❌ 代码编辑（永远只读）/ 运行 / 调试
- ❌ Git 集成 / 构建系统 / 依赖管理
- ❌ 插件市场 / 多人协作 / 云同步
- ❌ 代码生成（LLM 只解释）
- ❌ 云端托管（本地优先，不上传代码）
- ❌ MVP 阶段不做向量检索/语义搜索（推迟到二期）
- ❌ MVP 阶段不做"重要性标记/PageRank 阅读路径"（锦上添花，砍掉不影响闭环）
- ❌ MVP 阶段不做笔记/批注（涉及 schema 设计，移到二期，避免返工）
- ❌ 教程/课程内容

## 四、技术栈（最终决策）

| 维度 | 选型 | 理由 |
|------|------|------|
| **形态** | 本地优先：localhost 应用 → 后期套 Tauri 壳 | 三层解耦，代码 100% 复用 |
| **前端** | React + TypeScript + CodeMirror 6（只读）+ react-flow（调用图） | Web 生态丰富，虚拟滚动解决大文件 |
| **引擎** | Python：tree-sitter 绑定 + 符号解析 + FastAPI localhost 服务 | 引擎本质是 Python/Rust 生态的活 |
| **存储** | 每仓库一个 SQLite 文件：符号表、调用边、FTS5 全文索引、摘要缓存、标注 | 单用户单仓库本地工具，PostgreSQL 是架构 cosplay |
| **LLM** | BYO API Key + OpenAI 兼容协议网关（经本地引擎代理）；Ollama 作为后期彩蛋 | 本地代理顺手解决 CORS + key 暴露 + 多供应商适配 |
| **语言** | MVP 仅 Python；语言支持做成插件层（grammar + 符号查询 + 惯用法规则 + prompt 模板） | 真正成本在语义层不在解析；插件化让加 TS 变成一周的活 |

### 关键技术决策的论证

**1. 为什么 MVP 不要向量库？**（cc 的犀利洞察）
PRD 说的 RAG——"抓函数体 + 被调函数签名 + 类成员变量组装 prompt"——这**根本不是语义检索，是对符号表的确定性 SQL 查询**。有了符号表、调用边、类成员表，一次 JOIN 就拼出上下文了。Embedding + 向量库解决的是"我不知道符号叫什么名字，只记得大概意思"，那是二期锦上添花。

**2. 为什么"确定性上下文组装"必须进 MVP？**
没有它，问答就退化成"把选中代码丢给 ChatGPT"——用户自己复制粘贴也能做到，产品就没有存在理由了。它的成本在有了符号表之后几乎为零（几条 SQL），收益是回答质量的数量级差异。

**3. 为什么 LLM 要经本地引擎代理？**
从浏览器页面直调各家 LLM API 会遇到 CORS 限制和 key 暴露问题；本地引擎进程本来就要存在，让它顺便充当 LLM 网关，多供应商适配、key 管理、CORS 三个问题一次解决。用 OpenAI 兼容接口做适配标准，能直接覆盖 DeepSeek、智谱等大部分国产模型。

**4. Python 动态类型的诚实预期**
Python 动态类型意味着调用图永远做不到精确（duck typing、属性调用）。MVP 就按"名称保守匹配 + 列出多个候选调用点"来做，别追求完美解析，那是无底洞。

**5. 摘要生成策略：惰性，不批量**
"默认折叠 + 一句话摘要"不要在建索引时批量调 LLM 生成全库摘要——烧钱且大部分摘要永远不会被看到。改成**惰性生成**：用户第一次展开某函数时才生成，结果缓存进 SQLite，下次直接读。

## 五、MVP 最小闭环

cc 的逆耳忠言：PRD 的 MVP 清单（6 个模块）还是偏肥。真正最小的闭环是：

```
索引 → 文件树 → 折叠阅读 → 跳转 → 局部调用图 → 带上下文提问
```

"重要性标记/阅读路径"这类锦上添花的东西砍掉不会影响闭环验证。

**先让那把放大镜磨亮，再谈镜框雕花。**

### MVP 任务拆解（待用户确认后细化）

1. **引擎层**：tree-sitter Python 解析 → 符号表 + 调用边写入 SQLite + FTS5 索引
2. **服务层**：FastAPI 暴露符号查询/跳转/引用/调用图/LLM 网关接口
3. **前端**：文件树 + 只读代码视图（CodeMirror）+ 符号大纲 + 跳转交互
4. **前端**：局部调用图面板（react-flow）+ 全局搜索
5. **前端**：LLM 对话面板 + 确定性上下文组装 + 惰性摘要
6. **集成**：一条命令启动（`code-archmage <path>` → 打开 localhost）
